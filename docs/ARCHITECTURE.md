# Architecture

`Sdk` defines game-independent extension contracts. `Core` implements XML validation, bounded logging, reports, localization and test execution. `Mod` adapts these operations to Bannerlord and hosts the Gauntlet view and pipe server. `Desktop` is the WPF client. `Examples` demonstrates campaign and mission tests.

The SDK also owns SharedLibraryRegistry. Forge creates it on the first application update before notifying availability callbacks; module loading can occur on a different thread. `RegisterWhenAvailable` atomically checks the current registry and records a callback for later availability, so an extension cannot miss a connection between a null check and subscription. Provider and consumer module scopes publish and resolve explicit interface contracts with compatible major/minimum versions. Handles belong to a specific registration and become unusable on withdrawal, scope disposal or disconnect. Subscriber failures are collected after all availability callbacks have run. This isolates notification failures but does not roll back partial registrations. See SHARED_LIBRARIES.md for ownership and thread requirements.

The native module and optional desktop client are separate deployment units. Modules and developer ZIPs contain no EXE files. Only the Desktop ZIP contains the compiled Windows application. The native panel and SDK do not depend on launching that application.

Forge is a standalone module. Its production project references the local Bannerlord assemblies and Forge's own Core/SDK only; it has no build-time reference to Harmony, MCM, ButterLib, or a third-party mod library. Release validation rejects those framework DLLs from mod archives.

The transport thread queues requests. The application tick processes at most one request per frame on the game thread. XML scans and log persistence run off-thread. Inspectors copy an explicit allowlist of scalar properties rather than traversing arbitrary object graphs. The live inspector returns at most 200 matches per query; narrow the query to inspect additional objects.

In-memory logs keep 2,000 entries, with messages capped at 16,000 characters. Persistence retains 20 session log files. Tests keep 200 results, snapshots 100 objects, frame metrics 600 samples. Frame times describe the observed game tick; they do not identify a responsible mod. Event rates currently cover agent creation and deletion.

The adapter also retains 600 completed `OnApplicationTick` durations measured with `Stopwatch`. Metrics expose sample count, mean, p95 and maximum under `forge.callback.*`. This measures synchronous work inside the callback, including dispatched requests; it excludes background work, rendering elsewhere and the recorder itself. A metrics request observes earlier completed callbacks. See PERFORMANCE_SAMPLING.md for scope and measurement procedure.

Test scenarios record their selected seed, context, steps, initial inventory count where applicable and result. Third-party game behavior can introduce nondeterminism. The custom-battle example clones the player's character for one temporary agent; removal is requested with `FadeOut` and checked on subsequent updates until the agent is absent. Native execution/removal evidence and remaining coverage are recorded in VALIDATION.md.

Diagnostics inspect installed folders, not the launcher's selected load order. Missing dependencies and cycles are structural findings. XML parsing is strict, so an encoding defect may be reported even if the game tolerates it. Reports do not claim that every flagged file caused a crash. DLL lookup includes the game's shared binary directory.

ForgeWeave is Forge's original cooperative extension framework. `TestEngine` implements its additive `IForgeEventRegistry`, so `ForgeApi.Events` is available before `RegisterWhenAvailable` callbacks register their handlers. The native adapter queues only scalar data from official lifecycle callbacks, then drains at most 16 events per application update on the game thread. The queue is bounded to 128. `ContextLeaving` records its source context even when the live host has already entered the destination context. `ForgeEvent` copies at most 32 text pairs and exposes no game objects or services to handlers. SDK v3 adds bounded exact-match filters that are copied during registration and evaluated before authorization.

`ForgeWeaveEngine` computes a deterministic plan from event kind, priority and same-priority `Before`/`After` references. Missing, cross-event, cross-priority, self-referential and cyclic constraints block affected handlers rather than causing an inferred order. Each handler is authorized with the existing descriptor context, testing-mode and campaign-copy safeguards; errors are isolated, timed and quarantined after a declared bounded failure count. `Pulse` requires a per-handler interval of at least 250 ms in addition to the host's bounded pulse. Snapshots contain copied handler/event health, findings and the 64 most recent dispatches; reports, the native Framework action and desktop Framework section use this snapshot without reflection or game-object traversal. See [FORGEWEAVE.md](FORGEWEAVE.md).

Replay Lab extends that event boundary without changing it into a patch engine. After a host dispatch returns, Forge retains a bounded detached record of its sequence, event, logical context, timing, copied scalar payload and original outcome. Only handlers with an explicit replay mode are eligible. A replay references one retained source sequence, receives a new dispatch sequence, requires exact current-context equality and never becomes another retained source. Read-only verification can opt into `ObserveOnly`; `Live` still passes every descriptor-access, test-mode and copied-campaign check before a writer runs. The replay registry and local pipe do not accept an author-supplied payload or arbitrary callback. Snapshots and reports preserve source evidence, rejection reasons, timings and handler outcomes so authors can distinguish a rejected verification from a completed one. This is controlled event verification, not universal method interception or a replacement claim for every framework.

The optional historical Harmony Patch Atlas uses reflection only after a `HarmonyLib.Harmony` type is already loaded. It accepts only the public query surface, bounds discovery and text fields, and serializes method identity, owners, categories, declared priorities, before/after declarations and patch-method identity into reports. Targets with empty metadata are labeled as such rather than presented as active patch evidence. An explicit `harmony` request refreshes the bounded Atlas cache; report and export reuse that capture instead of silently rescanning on the game thread. Context changes mark the capture stale. It is isolated from ForgeWeave and not part of the recommended extension path.

Patch Blueprint Preflight is a second, standalone path for SDK authors. `IPatchBlueprintProvider` is additive to the v1 registry and returns copied, inert declarations on an explicit game-thread request. Core resolves each declaration only against already loaded assemblies using exact assembly/type/member/signature metadata. It does not load assemblies, call a patch engine, invoke the declared callback, or accept target reflection strings through the pipe. It records self-referential ordering declarations for review but never infers execution order. The latest explicit preflight is cached in reports and becomes stale after a context change. See [PATCH_BLUEPRINTS.md](PATCH_BLUEPRINTS.md).

Supported target: local Native 1.4.8. RBM and Vanguard are integration candidates, not certified compatible combinations. Multiplayer, scene editing, DLL hot reload, AI generation and automatic publication are excluded.

Primary API reference: [TaleWorlds module documentation](https://moddocs.bannerlord.com/asset-management/quickguide_create_a_mod/). Exact signatures were also inspected from the installed assemblies. Forge complements [BUTR crash reporting](https://github.com/BUTR/BUTR.CrashReport), rather than intercepting every exception or replacing it.
